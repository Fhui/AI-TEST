# 用例与输出规则

本文件只负责“测试点如何拆成用例，以及最终输出如何约束”。
它不是 PRD 结构化分析指南，也不是测试点建模指南。

在使用本文件前，应先阅读：

- [prd-structured-analysis.md](prd-structured-analysis.md)
- [testpoint-modeling.md](testpoint-modeling.md)

## 用例覆盖清单

检查 PRD 是否包含以下维度，并在抽象模型、正文或已确认的流程图/时序图有依据时生成对应测试用例：

- 对象
- 状态
- 行为
- 规则
- 状态流转
- 权限控制
- 外部依赖
- 异常路径
- 边界条件
- 补偿机制

如果某个维度未描述且无法安全推断，不要强行生成用例。应明确标注为 `PRD未说明` 或写入 `待确认项`。

## 图示补充规则

当 PRD 同时包含正文与图片时，按以下顺序使用信息：

- 先读正文，再识别图片类型，再参考 PlantUML 整理结果。
- 只有明确的流程图、时序图、泳道图才用于补充对象关系、分支节点、通知链路、状态节点等信息。
- 如果图片只展示页面样式、布局、表单、列表、按钮、弹窗或原型效果，则跳过流程分析与 PlantUML 转换。
- 如果图片与正文冲突，以正文为主，并将冲突点写入 `待确认项`。
- 如果图片可见流程节点但无法确认条件、时机或参与对象，应写 `待确认`，不要强补。
- 当 PlantUML 是从正文与已确认流程图整理出的中间产物时，测试点应基于两者共同支持的事实，而不是基于个人扩写。

## 用例拆分规则

拆分用例时遵循以下原则：

- 一条用例只验证一个核心点。
- 成功路径与失败路径分开。
- 每个主要规则单独成用例。
- 当权限差异会导致行为不同，应分别生成用例。
- 每个关键状态流转应独立成用例。
- 当边界条件对应的期望结果不同，应分别生成用例。
- 当依赖成功与依赖失败的结果不同，应分别生成用例。

避免以下反模式：

- 在同一条用例中混合多种独立验证点
- 把多个分支路径塞进一段冗长的 `ts`
- 使用“功能正常”这类模糊说法掩盖预期结果

## 用例编写规则

标题与步骤应具备足够的可执行性：

- `tc` 尽量包含明确的对象、行为、条件与预期结果。
- `ts` 按时间顺序书写。
- 重复性的准备动作放到 `tp`，不要挤进第一步。
- 在建模层先使用抽象概念，在最终用例层再映射为 PRD 原文术语。

当信息缺失时：

- 没有前置条件时使用 `tp: 无`
- 存在明显前提但 PRD 未定义时使用 `tp: PRD未说明`
- 不要猜测阈值、默认值或系统行为，应在步骤中或 `待确认项` 中写明 `PRD未说明`

## 用例优先级规则

除非 PRD 或用户另有要求，否则默认按以下基线确定优先级：

- `P0`：核心对象生命周期、关键状态变化、关键权限、不可逆行为、安全相关或高业务影响场景
- `P1`：主行为路径、重要规则校验、关键分支、常见异常路径、高频状态迁移
- `P2`：次要异常路径、边界条件、低频规则校验、依赖异常或补偿逻辑
- `P3`：低风险文案、弱约束兼容性检查、补充性覆盖

若 PRD 明确体现更高业务风险，可提高优先级。若风险不明确，则沿用基线，不要夸大严重程度。

## 输出中的推断规则

仅在文档提供足够依据时才允许推断：

- 从标题、上下文和边界说明推断 `系统`
- 从修订信息、发布标识或迭代信息推断 `版本`
- 从标题层级、流程片段、行为聚类与对象边界推断 `模块`

凡是使用了推断，都必须：

- 在推断结果后追加 `（待确认）`
- 在 `待确认项` 中说明推断依据

如果推断仍然过于主观，应直接使用 `系统待确认` / `版本待确认` / `模块待确认`。

## 输出前检查项

输出前逐项确认：

- 每条用例都位于某个模块下
- 每条用例都包含 `tc`、`ts`、`ti`、`tp`
- 每一步都单独写一条 `ts`
- 每条 `ts` 后直接跟步骤内容，不要带步骤编号
- 每条 `ts` 下都要补一个子节点 `xxx`
- 除 `tc:`、`ts:`、`ti:`、`tp:` 外，其他位置不要使用冒号
- 每个 `ti` 都是 `P0 / P1 / P2 / P3` 之一
- 没有凭空补充任何 PRD 未支持的业务规则
- 所有歧义点都已写入 `待确认项`
