# 测试点建模

## 目标

在完成 PRD 结构化分析之后，不要立刻写测试用例。
必须先把需求映射成“测试点模型”，再把测试点落成用例。

`testpoint-model.md` 不是分析摘要，也不是 `structured-analysis.md` 的缩写版。
它只保留可直接驱动测试用例生成的测试点。
禁止把完整结构化分析内容复制进 `testpoint-model.md`。

本文件禁止直接围绕具体业务名词列测试点。
必须先基于抽象模型建模：

- 对象
- 状态
- 行为
- 规则
- 依赖

## 强制建模输出

每个模块至少要输出一份测试点模型，并通过 `file-system-mcp` 的 `write_file` 落盘到 `./<delivery-name>/analysis/testpoint-model.md`，建议至少覆盖以下类别：

- 主路径测试
- 分支路径测试
- 异常路径测试
- 状态测试
- 权限测试
- 数据约束测试
- 通知测试
- 场景测试
- 失败补偿测试

如果某一类在 PRD 中完全没有依据，可以不展开，但必须明确写 `PRD未说明` 或记录到 `待确认项`。

每个测试点必须能追溯到 `structured-analysis.md` 中的对象、状态、行为、规则或依赖。
如果测试点无法追溯到这些建模元素，禁止写入 `testpoint-model.md`。

测试点必须是可执行用例的上一级粒度：

- 能拆成一条或多条测试用例
- 有明确验证目标
- 有明确触发对象或行为
- 有明确预期方向
- 不承载完整分析过程
- 不复制对象模型、状态机、行为模型、数据规则、权限模型、系统行为的完整内容

## 建模前提

测试点建模必须建立在以下前提之上：

- 已识别核心对象
- 已识别对象状态
- 已识别状态迁移
- 已识别触发状态变化的行为
- 已识别外部依赖、权限、失败机制、边界条件

如果前提不完整，应先回到 `prd-structured-analysis.md` 补分析，而不是继续写测试点。

## 建模顺序

建议按以下顺序为每个模块建模：

### 1. 主路径测试

回答：

- 这个模块最核心的成功路径是什么
- 对象从什么状态进入流程
- 经过哪些关键行为
- 最终进入什么目标状态

主路径通常对应“对象在正常规则下从初始状态进入目标状态”的成功路径。

### 2. 分支路径测试

回答：

- 同一主流程下有哪些分支
- 不同条件下系统走向是否不同
- 不同对象类型、状态组合、规则命中结果是否进入不同分支

典型分支包括：

- 不同对象类型
- 不同状态组合
- 不同行为入口
- 不同规则命中结果
- 不同依赖返回结果

### 3. 异常路径测试

回答：

- 当输入非法、依赖失败、条件不满足时会怎样
- 是否有错误提示
- 是否会阻断流程
- 是否产生脏数据

典型异常包括：

- 输入非法
- 规则不满足
- 外部依赖失败
- 异步处理失败
- 通知失败
- 状态不允许

### 4. 状态测试

回答：

- 模块中有哪些状态
- 状态如何进入
- 状态如何退出
- 状态之间是否允许跳转
- 不同状态下允许哪些行为

典型状态测试包括：

- 初始 -> 生效
- 生效 -> 待失效
- 待失效 -> 已失效
- 已失效 -> 恢复
- 状态禁止跳转

### 5. 权限测试

回答：

- 谁可以查看
- 谁可以操作
- 谁可以新增
- 谁只能读
- 数据范围如何受权限或范围约束

至少考虑：

- 菜单权限
- 页面操作权限
- 数据范围权限
- 组织范围权限

### 6. 数据约束测试

回答：

- 字段约束有哪些
- 搜索规则有哪些
- 批量处理约束有哪些
- 去重与唯一性如何处理
- 边界值如何处理

典型数据测试包括：

- 格式约束
- 长度约束
- 唯一性约束
- 枚举约束
- 边界值约束
- 集合或批量处理约束

### 7. 通知测试

通知需求必须单独建模，不要散落到其他类型里。

回答：

- 什么事件触发通知
- 通知谁
- 通知内容是否完整
- 通知时机是否正确
- 是否存在重复通知或漏通知

典型通知测试包括：

- 成功事件通知
- 失败事件通知
- 延迟触发通知
- 超时提醒通知
- 状态变更通知

### 8. 场景测试

场景测试关注多个规则叠加后的真实业务情况。

回答：

- 哪些组合场景最容易出错
- 哪些特殊身份或关系会影响结果
- 哪些时间窗口或依赖状态会改变处理逻辑

典型场景包括：

- 多对象关联场景
- 多状态叠加场景
- 多规则叠加场景
- 特殊身份场景
- 时间窗口场景
- 数据缺失场景

### 9. 失败补偿测试

这是最容易遗漏的一类。

回答：

- 某步失败后系统如何恢复
- 是否允许重试
- 是否有回滚
- 是否有后续补发或重新处理

典型补偿包括：

- 失败后重试
- 失败后回滚
- 超时后补发
- 失效后恢复
- 依赖恢复后重新处理

## 8 个问题到测试点的映射

测试点必须显式映射自以下问题：

1. 核心对象是什么 -> 对象覆盖测试点
2. 对象状态是什么 -> 状态覆盖测试点
3. 状态如何流转 -> 状态迁移测试点
4. 什么行为触发状态变化 -> 行为触发测试点
5. 是否存在延迟、异步或外部依赖 -> 依赖与时序测试点
6. 是否存在权限控制 -> 权限测试点
7. 是否存在失败或回滚机制 -> 异常与补偿测试点
8. 是否存在边界条件或极端情况 -> 边界与场景测试点

如果一个模块的测试点无法映射回这 8 个问题，说明建模还不完整。

## 追溯要求

每个测试点必须包含最小追溯信息，但不要复制完整分析内容。

追溯字段只允许记录以下摘要：

- 来源对象
- 来源状态
- 来源行为
- 来源规则
- 来源依赖
- 来源分析章节

追溯信息用于证明测试点来自 `structured-analysis.md`，而不是重新展开结构化分析。

禁止在测试点中复制以下内容：

- 完整 Domain Model
- 完整 State Machine
- 完整 Behavior Model
- 完整 Data Rules
- 完整 Permission Model
- 完整 System Behavior
- 大段 PRD 原文
- 大段 PlantUML 内容

## 从测试点到测试用例的映射

建模完成后，再把每个测试点映射为用例。

映射规则：

- 一个核心测试点对应一条用例
- 同一测试点的不同结果分支，应拆成不同用例
- 一条用例不要同时验证多个类别

例如：

- 主路径测试点 -> 正常行为用例
- 异常路径测试点 -> 失败行为用例
- 状态测试点 -> 状态迁移用例
- 通知测试点 -> 通知时机与内容用例

## 约束

- 先建模，后写用例。
- 没有经过测试点建模，不要直接输出最终用例树。
- 如果某模块只有主路径，没有异常、状态、权限等建模结果，应主动检查是否漏分析，而不是直接认为“不需要”。
- 禁止直接围绕具体业务实体堆测试点。
- 必须先基于对象、状态、行为、规则、依赖建立抽象测试点模型。
- 禁止把 `structured-analysis.md` 的完整内容复制进 `testpoint-model.md`。
- 禁止把 `testpoint-model.md` 写成分析摘要。
- 禁止写入无法追溯到对象、状态、行为、规则或依赖的测试点。
